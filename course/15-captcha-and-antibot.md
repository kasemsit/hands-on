# บทที่ 15 · CAPTCHA และสถาปัตยกรรม Anti-bot

> CAPTCHA เป็นเพียง**หนึ่งชั้น**ในระบบป้องกันทั้งหมด
> และมักไม่ใช่ชั้นที่สำคัญที่สุดด้วย

## 15.1 เราป้องกันอะไรกันแน่

ก่อนออกแบบ ต้องตอบให้ได้ว่ากำลังกันอะไร เพราะแต่ละอย่างใช้เครื่องมือคนละตัว:

| ภัย | ตัวอย่าง | เครื่องมือที่ได้ผล |
|-----|----------|-------------------|
| **Credential stuffing** | เอา user/pass ที่รั่วจากเว็บอื่นมาลองไล่ | rate limit ตาม account, 2FA, ตรวจ password ที่รั่ว |
| **Brute force** | เดารหัสผ่านคนเดียวซ้ำ ๆ | rate limit + หน่วงเวลาเพิ่มขึ้น + lockout ชั่วคราว |
| **Scraping** | ดูดข้อมูลทั้งเว็บ | rate limit, PoW, ตรวจ pattern การเข้าถึง |
| **Spam** | สมัครสมาชิก/โพสต์อัตโนมัติ | CAPTCHA, honeypot, ยืนยันอีเมล |
| **Scalping** | กวาดซื้อของ/จองคิว | คิว, PoW ยาก, ยืนยันตัวตน |
| **Card testing** | ทดสอบบัตรที่ขโมยมา | rate limit ที่ payment, ตรวจ velocity |
| **DDoS** | ถล่มให้ล่ม | CDN/WAF (**CAPTCHA ช่วยไม่ได้**) |

> **ข้อสังเกตสำคัญ: rate limiting ปรากฏในเกือบทุกแถว แต่ CAPTCHA ปรากฏแค่ 2 แถว**
> นี่คือเหตุผลที่ควรทำ rate limit ให้ดีก่อนคิดเรื่อง CAPTCHA

## 15.2 ชั้นการป้องกัน (จากถูกไปแพง)

```
     ชั้นที่ 1  Rate limiting                 ← ทำก่อนเสมอ ได้ผลคุ้มที่สุด
     ชั้นที่ 2  Honeypot / field ล่อ          ← ถูกมาก ไม่กวนผู้ใช้เลย
     ชั้นที่ 3  Proof of Work (ALTCHA)        ← ไม่กวนผู้ใช้ แต่กินเวลาบอท
     ชั้นที่ 4  Fingerprinting / behavior      ← ซับซ้อน มี false positive
     ชั้นที่ 5  CAPTCHA แบบให้คนทำ            ← กวนผู้ใช้มาก ใช้เมื่อจำเป็น
     ชั้นที่ 6  ยืนยันตัวตน (SMS/บัตร/KYC)     ← แพงและกวนที่สุด
```

**หลักการ: ใช้ชั้นที่ต่ำที่สุดที่แก้ปัญหาได้**
และควร**ยกระดับตามความเสี่ยง** (risk-based) ไม่ใช่บังคับทุกคนเท่ากัน:

```
ผู้ใช้ปกติ            → ผ่านฉลุย ไม่เจออะไรเลย
มีสัญญาณน่าสงสัย       → PoW เงียบ ๆ (ผู้ใช้ไม่รู้ตัว)
น่าสงสัยมาก           → CAPTCHA แบบให้คนทำ
เกือบแน่ใจว่าเป็นบอท    → บล็อก
```

## 15.3 Honeypot — ถูกที่สุด คุ้มที่สุด

ใส่ field ที่คนมองไม่เห็น แต่บอทที่กรอกทุกช่องจะกรอก

```html
<div style="position:absolute;left:-9999px" aria-hidden="true">
  <label>อย่ากรอกช่องนี้</label>
  <input type="text" name="website" tabindex="-1" autocomplete="off">
</div>
```

ถ้า `website` มีค่า → เป็นบอทเกือบแน่นอน

**เทคนิคเพิ่มเติมที่ได้ผลดี:**

- **จับเวลา**: ถ้ากรอกฟอร์มเสร็จภายใน 2 วินาที = ไม่ใช่มนุษย์
  (เก็บ timestamp ตอนแสดงฟอร์ม แล้วเซ็นด้วย HMAC — [บทที่ 13](13-webhooks-and-hmac.md))
- **ใช้ชื่อ field ที่ล่อ**: `email_confirm`, `url`, `phone2` ดูสมจริงกว่า `honeypot`
- **อย่าใช้ `type="hidden"`** บอทที่ฉลาดข้าม hidden field แต่กรอก text field ที่ซ่อนด้วย CSS

**ข้อดี**: ผู้ใช้จริงไม่เจออะไรเลย, ทำง่ายมาก, ไม่มี false positive กับคนทั่วไป
**ข้อเสีย**: บอทที่เขียนมาเจาะเว็บคุณโดยเฉพาะจะข้ามได้ (ต้องระวังเรื่อง screen reader ด้วย — ใช้ `aria-hidden`)

## 15.4 CAPTCHA แบบต่าง ๆ

| แบบ | ตัวอย่าง | ผู้ใช้ | บอทสมัยนี้ผ่านได้ไหม |
|-----|----------|--------|---------------------|
| ตัวอักษรบิดเบี้ยว | เก่า | 😖 แย่มาก | ✅ OCR ผ่านสบาย |
| เลือกภาพ | reCAPTCHA v2 | 😐 น่ารำคาญ | ✅ AI ทำได้ดีกว่าคน |
| คะแนนพฤติกรรม | reCAPTCHA v3, Turnstile | 🙂 ไม่เห็นอะไร | ⚠️ ยากขึ้น |
| **Proof of Work** | **ALTCHA**, Friendly Captcha | 🙂 แค่รอแป๊บ | ⚠️ ผ่านได้ แต่**ต้องจ่าย CPU** |
| Cryptographic attestation | Private Access Tokens | 🙂 | ⚠️ ยากมาก แต่ผูกกับ Apple/Google |

**ความจริงที่ต้องยอมรับ: AI แก้ CAPTCHA แบบภาพได้ดีกว่ามนุษย์แล้ว**
และมีบริการรับจ้างแก้ CAPTCHA ด้วยแรงงานคนในราคาหลักสตางค์ต่อครั้ง

ดังนั้น CAPTCHA สมัยใหม่ไม่ได้พยายาม "ทำให้ผ่านไม่ได้" แต่พยายาม
**ทำให้การผ่านมีต้นทุน** — ซึ่งเป็นแนวคิดที่ต่างกันมาก

**ประเด็นเรื่องความเป็นส่วนตัวและการเข้าถึง:** reCAPTCHA ส่งข้อมูลผู้ใช้ให้ Google
และ CAPTCHA แบบภาพกีดกันผู้พิการทางสายตา — ALTCHA/PoW ไม่มีปัญหาทั้งสองข้อ
นี่คือเหตุผลหลักที่คนเลือกใช้มัน (นอกจากเรื่องที่มันเป็น open source)

## 15.5 Proof of Work — ทำไมถึงได้ผล

แนวคิด: บังคับให้ client **จ่ายค่า CPU** ก่อนถึงจะยิง request ได้

```
ผู้ใช้จริง 1 คน     : 1 request  × 0.3 วินาที  = แทบไม่รู้สึก
บอทที่ยิง 100,000   : 100,000 × 0.3 วินาที  = 8 ชั่วโมง CPU
```

**ความไม่สมมาตรนี้คือหัวใจ** — แพงสำหรับคนทำเยอะ ถูกสำหรับคนทำครั้งเดียว

- คำนวณคำตอบ: **ช้า** (ต้องลองไปเรื่อย ๆ)
- ตรวจคำตอบ: **เร็วมาก** (hash ครั้งเดียว)

**ข้อจำกัดที่ต้องรู้:**

| ข้อจำกัด | รายละเอียด |
|----------|-----------|
| ไม่กัน "บอทที่ยอมจ่าย" | ถ้าของที่ขโมยมีค่ามากกว่าค่า CPU ก็ยังคุ้ม |
| CPU ไม่เท่ากัน | เซิร์ฟเวอร์แรง ๆ ทำได้เร็วกว่ามือถือเก่า 50 เท่า |
| กระทบผู้ใช้มือถือรุ่นเก่า | ต้องตั้ง difficulty ให้พอดี |
| ปรับ difficulty ตามความเสี่ยงจะดีกว่า | ผู้ใช้ปกติได้โจทย์ง่าย ผู้ต้องสงสัยได้โจทย์ยาก |

รายละเอียดเชิงเทคนิคของ ALTCHA อยู่ในบทถัดไป

## 15.6 Fingerprinting

เก็บคุณสมบัติของ client มาประกอบเป็น "ลายนิ้วมือ"

| ระดับ | เก็บอะไร | บอทปลอมยากแค่ไหน |
|-------|----------|-------------------|
| HTTP | User-Agent, ลำดับ header, `Accept-*` | ง่าย |
| TLS | **JA3/JA4** — ลายเซ็นจาก cipher suite ที่เสนอมา | **ยาก** ต้องแก้ TLS stack |
| HTTP/2 | ลำดับ SETTINGS frame, priority | ยาก |
| Browser | canvas, WebGL, font, timezone, หน้าจอ | ปานกลาง |
| Behavior | การเคลื่อนเมาส์, จังหวะพิมพ์, scroll | ปานกลาง |

**JA3/JA4 คือเหตุผลที่ curl ถูกจับได้ง่าย** — ไม่ว่าคุณจะตั้ง User-Agent
เป็น Chrome แค่ไหน TLS handshake ของ curl (OpenSSL) ก็ต่างจาก Chrome (BoringSSL)
อย่างชัดเจนตั้งแต่ byte แรก

> ⚠️ **ข้อควรระวังสำหรับคนทำ API**: fingerprinting มี false positive สูง
> ผู้ใช้ที่ใช้ VPN, ปิด JS, ใช้เบราว์เซอร์ที่เน้นความเป็นส่วนตัว หรือใช้ screen reader
> จะดูเหมือนบอท ถ้าบล็อกแรงเกินไปคุณจะเสียลูกค้าจริงโดยไม่รู้ตัว
> — ควร log ไว้ก่อนสัก 2 สัปดาห์ ดูว่าจะบล็อกใครบ้าง แล้วค่อยเปิดใช้

## 15.7 Rate limiting — ชั้นที่คุ้มค่าที่สุด

(รายละเอียดการทำอยู่ใน[บทที่ 12](12-api-design-practices.md))

**จำกัดตามอะไรได้บ้าง และแต่ละอันมีจุดอ่อนอะไร:**

| จำกัดตาม | จุดอ่อน |
|----------|---------|
| IP | ผู้ใช้หลังเน็ตองค์กร/มือถือใช้ IP ร่วมกัน + botnet มี IP เป็นหมื่น |
| Account | ผู้โจมตีสมัครบัญชีใหม่ได้ / lock บัญชีคนอื่นได้ |
| API key | คนที่มี key อยู่แล้วเท่านั้น |
| Fingerprint | ปลอมได้ |
| ASN / ช่วง IP | บล็อก data center ทั้งก้อน (AWS, GCP) ได้ผลดีกับ scraper |

**ทำหลายชั้นพร้อมกันเสมอ** และตอบด้วย `429 + Retry-After` ไม่ใช่ตัดการเชื่อมต่อเงียบ ๆ
(การตอบอย่างสุภาพช่วยให้ client ที่สุจริตปรับตัวได้)

## 15.8 การป้องกันฝั่ง mobile app ของคุณ

ถ้าคุณอยากมั่นใจว่า request มาจากแอปจริง ไม่ใช่คนที่ reverse-engineer API:

| วิธี | ได้ผลแค่ไหน |
|------|-------------|
| API key ฝังในแอป | ❌ แกะได้ใน 30 วินาที |
| Certificate pinning | ⚠️ กันการดักดู แต่ patch แอปให้ปิดได้ |
| Request signing ด้วย key ในแอป | ⚠️ ดีกว่า แต่ key ก็ถูกแกะได้ |
| **Play Integrity API** (Android) | ✅ Google รับรองว่าแอปแท้บนเครื่องแท้ |
| **App Attest / DeviceCheck** (iOS) | ✅ Apple รับรอง |
| Obfuscation (R8/ProGuard) | ⚠️ แค่ทำให้ช้าลง ไม่ได้กัน |

**ความจริงที่ต้องยอมรับ: คุณควบคุม client ไม่ได้เลย**
ทุกอย่างที่รันบนเครื่องผู้ใช้ ถูกแก้ได้หมด

> **กฎเหล็ก: อย่าให้ความปลอดภัยขึ้นกับสิ่งที่เกิดขึ้นฝั่ง client**
> validate ทุกอย่างที่ server เสมอ ถือว่า client ทุกตัวอาจเป็นศัตรู
>
> Play Integrity / App Attest ช่วย**เพิ่มต้นทุน**ให้ผู้โจมตี แต่ไม่ใช่กำแพงเหล็ก
> และมันจะกันผู้ใช้ที่ root เครื่องหรือใช้ ROM ทางเลือกด้วย — ตัดสินใจให้ดี

## 15.9 อย่าลืมวัดผล

ระบบ anti-bot ที่ไม่มีการวัดผลคือการเดา ควรเก็บ:

- อัตราการผ่าน/ไม่ผ่านแต่ละชั้น
- **false positive**: ผู้ใช้จริงที่ถูกบล็อก (วัดจากคำร้องเรียน + conversion rate ที่ตก)
- ต้นทุน: เวลาที่ผู้ใช้เสียไป, ค่าบริการ third-party
- ผลจริง: spam ลดลงเท่าไร

**ถ้าเปิดระบบใหม่แล้ว conversion rate ตก 5% แต่ spam ลด 2% นั่นคือขาดทุน**

## แบบฝึกหัด

1. เพิ่ม honeypot field ให้ `/search` ใน [lab/server.py](../lab/server.py)
   แล้วทดสอบว่ายิงด้วย curl พร้อม field นั้นจะถูกปฏิเสธ
2. เพิ่มการจับเวลา: ถ้า POST กลับมาเร็วกว่า 2 วินาทีหลังโหลดฟอร์ม ให้ปฏิเสธ
   (ใช้ HMAC เซ็น timestamp ตาม[บทที่ 13](13-webhooks-and-hmac.md) อย่าเชื่อ timestamp ที่ client ส่งมาเปล่า ๆ)
3. เปรียบเทียบ TLS fingerprint: `curl -v https://example.com` vs เบราว์เซอร์
   (ดูที่ cipher suite และ ALPN) — ต่างกันตรงไหน
4. ออกแบบระบบ anti-bot สำหรับหน้า login ของ API คุณ โดยเลือกใช้เฉพาะชั้นที่จำเป็น
   แล้วเขียนเหตุผลกำกับแต่ละชั้น
5. คำนวณ: ถ้าตั้ง PoW ให้ใช้เวลา 0.5 วินาทีบนมือถือทั่วไป
   บอทที่มี CPU เร็วกว่า 20 เท่าและรัน 100 threads จะยิงได้กี่ request ต่อชั่วโมง
   — PoW ยังช่วยไหม

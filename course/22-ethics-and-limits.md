# บทที่ 22 · จริยธรรมและขอบเขต

> ทักษะในคอร์สนี้ใช้สร้างและใช้ทำลายได้พอ ๆ กัน
> บทนี้สั้นแต่สำคัญที่สุด

## 22.1 เส้นแบ่งที่ชัดเจน {#s22-1}

| ✅ ทำได้สบายใจ | ⚠️ ต้องระวัง | ❌ อย่าทำ |
|----------------|--------------|-----------|
| ทดสอบระบบของตัวเอง | scrape ข้อมูลสาธารณะปริมาณมาก | เจาะระบบคนอื่นโดยไม่ได้รับอนุญาต |
| ใช้ API ตามที่เขาให้มา | automate บัญชีของตัวเองบนเว็บคนอื่น | หลบ CAPTCHA เพื่อสแปม/สร้างบัญชีปลอม |
| อ่านข้อมูลสาธารณะพอประมาณ | ใช้ข้อมูลที่ scrape มาเชิงพาณิชย์ | credential stuffing / brute force |
| ทดสอบ **ที่มีเอกสารอนุญาต** | เก็บข้อมูลส่วนบุคคล | ยิงจนระบบเขาล่ม |
| เรียนรู้จาก lab บนเครื่องตัวเอง | bypass rate limit ด้วย IP หลายตัว | ขายเครื่องมือหลบ anti-bot |

**คำถามสามข้อที่ควรถามตัวเองก่อนลงมือ:**

1. ถ้าเจ้าของระบบเห็นสิ่งที่ผมทำ เขาจะโอเคไหม
2. ถ้ามีคนทำแบบนี้กับระบบของผม ผมจะรู้สึกยังไง
3. ผมอธิบายสิ่งที่ทำให้คนอื่นฟังได้อย่างสบายใจไหม

ถ้าตอบ "ไม่" ข้อไหน ให้หยุด

## 22.2 กฎหมายไทยที่เกี่ยวข้อง {#s22-2}

> ⚠️ ผมไม่ใช่นักกฎหมาย ส่วนนี้เป็นข้อมูลทั่วไปเพื่อให้รู้ว่าควรระวังเรื่องอะไร
> **เรื่องที่มีความเสี่ยงจริงควรปรึกษาทนายความ**

**พ.ร.บ. คอมพิวเตอร์ พ.ศ. 2550 (แก้ไข 2560)** — มาตราที่เกี่ยวข้อง:

| มาตรา | เกี่ยวกับ |
|-------|----------|
| ม.5 | เข้าถึงระบบคอมพิวเตอร์ที่มีมาตรการป้องกันโดยมิชอบ |
| ม.7 | เข้าถึงข้อมูลคอมพิวเตอร์ที่มีมาตรการป้องกันโดยมิชอบ |
| ม.9 | แก้ไข/ทำลายข้อมูลของผู้อื่นโดยมิชอบ |
| ม.10 | รบกวนระบบจนใช้งานไม่ได้ (DoS) |

**ข้อสังเกตสำคัญ: "มาตรการป้องกัน" รวมถึง CAPTCHA และ rate limit**
การจงใจหลบเลี่ยงจึงอาจถูกตีความว่าเข้าข่าย — โดยเฉพาะเมื่อทำกับระบบของคนอื่น

**PDPA (พ.ร.บ. คุ้มครองข้อมูลส่วนบุคคล 2562)** — ถ้าคุณเก็บข้อมูลส่วนบุคคล
(ชื่อ อีเมล เบอร์โทร รูป IP address) ต้องมีฐานทางกฎหมายในการเก็บ
**"ข้อมูลเปิดเผยสาธารณะ" ไม่ได้แปลว่าเก็บไปใช้ได้อิสระ**

ต่างประเทศ: สหรัฐฯ มี CFAA, ยุโรปมี GDPR — ถ้าระบบหรือผู้ใช้อยู่ต่างประเทศ
กฎหมายเหล่านั้นอาจมีผลด้วย

## 22.3 robots.txt และ Terms of Service {#s22-3}

```bash
curl -s https://example.com/robots.txt
```

```
User-agent: *
Disallow: /admin/
Crawl-delay: 10
```

**robots.txt ไม่ใช่กฎหมาย** แต่:

- เป็นการแสดงเจตนาชัดเจนของเจ้าของเว็บ
- การจงใจฝ่าฝืนใช้เป็นหลักฐานว่า "รู้อยู่แล้วว่าเขาไม่อนุญาต" ได้
- `Crawl-delay` บอกความถี่ที่เขารับได้ — ควรเคารพ

**Terms of Service** มีน้ำหนักมากกว่า เพราะเป็นสัญญาที่คุณตกลงตอนสมัครใช้บริการ
เว็บส่วนใหญ่มีข้อห้าม automated access ชัดเจน การละเมิดอาจนำไปสู่การปิดบัญชี
และในบางกรณีคดีแพ่ง

## 22.4 มารยาทของ client ที่ดี {#s22-4}

ถ้าตัดสินใจแล้วว่าจะยิง automated request:

- [ ] **ระบุตัวตน** ใน User-Agent
      ```
      User-Agent: MyResearchBot/1.0 (+https://myapp.com/bot; contact@myapp.com)
      ```
- [ ] **หน่วงเวลา** อย่างน้อย 1 วินาทีต่อ request (มากกว่านั้นถ้าเป็นเว็บเล็ก)
- [ ] **เคารพ 429 และ `Retry-After`** — อย่ายิงต่อทันที
- [ ] **หยุดเมื่อเจอ 5xx ติดกัน** อาจเป็นเพราะคุณทำให้เขาล่ม
- [ ] **แคชผลลัพธ์** อย่าดึงข้อมูลเดิมซ้ำ ๆ (ใช้ ETag/If-Modified-Since)
- [ ] **ยิงนอกเวลา peak** ถ้าเป็นงานปริมาณมาก
- [ ] **ใช้ API ถ้ามี** — เร็วกว่า เสถียรกว่า และเขาตั้งใจให้ใช้
- [ ] **ติดต่อขออนุญาต** ถ้าต้องการข้อมูลปริมาณมาก
      (หลายที่ยินดีให้ dump ตรง ๆ ถ้าถาม ซึ่งง่ายกว่าการ scrape มาก)

## 22.5 การทดสอบความปลอดภัย {#s22-5}

**ก่อนทดสอบระบบใด ๆ ที่ไม่ใช่ของคุณ ต้องมี "อนุญาตเป็นลายลักษณ์อักษร"** ที่ระบุ:

- ขอบเขต (โดเมน/IP ไหนบ้าง — และอะไรที่**ห้าม**แตะ)
- ช่วงเวลาที่อนุญาต
- ประเภทการทดสอบที่ทำได้ (ห้าม DoS เกือบเสมอ)
- ช่องทางติดต่อฉุกเฉิน
- ข้อตกลงเรื่องการเปิดเผยข้อมูลที่พบ

**"เว็บเขาเปิดให้เข้าถึงได้" ไม่ใช่การอนุญาต** — ประตูบ้านที่ไม่ได้ล็อก
ไม่ได้แปลว่าเชิญให้เข้าไป

ถ้าอยากฝึกอย่างถูกกฎหมาย มีสนามให้เล่นเยอะมาก:

- **bug bounty**: HackerOne, Bugcrowd (มี scope ชัดเจน มีเงินรางวัลด้วย)
- **CTF**: picoCTF, HackTheBox, TryHackMe
- **สนามฝึกที่ตั้งใจทำให้เจาะ**: DVWA, WebGoat, Juice Shop
- **lab ในคอร์สนี้** — บนเครื่องคุณเอง ทำอะไรก็ได้

## 22.6 ถ้าเจอช่องโหว่โดยบังเอิญ {#s22-6}

1. **หยุดทันที** อย่าเจาะลึกต่อ อย่าดูข้อมูลของผู้ใช้จริง
2. **อย่าดาวน์โหลดข้อมูล** แม้เพื่อ "พิสูจน์"
3. หา `security.txt`: `curl -s https://example.com/.well-known/security.txt`
4. รายงานอย่างสุภาพ ให้รายละเอียดพอที่เขาจะทำซ้ำได้
5. ให้เวลาเขาแก้ (90 วันเป็นมาตรฐานสากล) ก่อนเปิดเผย
6. **อย่าเรียกร้องเงิน** — นั่นคือการขู่กรรโชก ไม่ใช่ responsible disclosure

## 22.7 กลับด้าน: คุณคือคนทำระบบ {#s22-7}

คอร์สนี้สอนทั้งสองด้านโดยตั้งใจ **การรู้ว่าคนโจมตีคิดยังไง ทำให้คุณป้องกันได้ดีขึ้น**
สรุปสิ่งที่ควรทำกับ API ของคุณ:

- ทำ rate limit ตั้งแต่วันแรก ([บทที่ 12](12-api-design-practices.md))
- validate ทุกอย่างที่ server — **อย่าเชื่อ client** ([บทที่ 15](15-captcha-and-antibot.md))
- ตอบ error เท่ากันเสมอเพื่อกัน user enumeration ([บทที่ 11](11-mobile-api-auth-design.md))
- log พอที่จะสืบสวนได้ แต่ไม่ log ความลับ ([บทที่ 12](12-api-design-practices.md))
- token อายุสั้น + revoke ได้ ([บทที่ 11](11-mobile-api-auth-design.md))
- มี `security.txt` และช่องทางรับรายงานช่องโหว่
- ตอบคนที่รายงานช่องโหว่อย่างสุภาพ — เขาช่วยคุณอยู่

## แบบฝึกหัด

1. อ่าน `robots.txt` และ ToS ของเว็บที่คุณใช้บ่อย 3 เว็บ ว่าเขาว่าอย่างไรเรื่อง automation
2. หา `security.txt` ของเว็บใหญ่ ๆ ดูว่าเขาให้ติดต่อทางไหน
3. เขียน `security.txt` สำหรับ API ของคุณเอง
4. ทบทวน: สิ่งที่คุณกำลังทำอยู่ตอนนี้ ผ่านคำถาม 3 ข้อในหัว[ข้อ 22.1](#s22-1) ไหม
5. เขียนนโยบาย rate limit ของ API คุณเป็นเอกสารสาธารณะ
   (โควตาเท่าไร ตอบอะไรเมื่อเกิน ขอเพิ่มได้ไหม)

# บทที่ 61 · Digital forensics — สืบหาว่าเกิดอะไรขึ้น

> [บทที่ 41](41-detection-and-response.md) สอนตอบสนองเหตุ **บทนี้สอนเก็บหลักฐานและไล่ลำดับเหตุการณ์**
> ให้ตอบได้ว่า *เข้ามาทางไหน · ทำอะไรไปบ้าง · เอาข้อมูลออกไปหรือเปล่า*

## 61.1 กฎข้อแรก — อย่าทำลายหลักฐานก่อนเก็บ {#s61-1}

**สัญชาตญาณแรกของทุกคนคือสิ่งที่ผิดที่สุด**

| สัญชาตญาณ | ทำไมผิด |
|---|---|
| รีบูตเครื่อง | 🔴 **หน่วยความจำหายหมด** — มัลแวร์หลายตัวอยู่แต่ใน RAM |
| ลบไฟล์ที่น่าสงสัย | ทำลายหลักฐาน |
| ติดตั้งเครื่องมือลงเครื่องที่โดน | เขียนทับข้อมูลที่ยังกู้ได้ |
| ปิดเครื่องทันที | ตัดสินใจได้ แต่ต้องรู้ว่าแลกอะไร |

```
เก็บก่อน → วิเคราะห์ทีหลัง
```

**ลำดับความผันผวนของหลักฐาน** — เก็บจากบนลงล่าง:

```
1. CPU register / cache      หายทันที
2. RAM                       หายเมื่อดับเครื่อง        ← สำคัญที่สุด
3. สถานะเครือข่าย            หายเร็ว
4. process ที่กำลังรัน
5. ดิสก์                      อยู่ได้นาน
6. backup / log ที่ส่งออกไปแล้ว  อยู่นานที่สุด
```

> **RAM คือจุดที่คนพลาดบ่อยที่สุด** — มัลแวร์สมัยใหม่จำนวนมากไม่แตะดิสก์เลย
> (fileless — [บทที่ 39](39-how-malware-works.md)) รีบูตเครื่องหนึ่งครั้งเท่ากับทำลายหลักฐานทั้งหมด

## 61.2 Chain of custody — ถ้าจะใช้ทางกฎหมาย {#s61-2}

**ถ้าเรื่องอาจไปถึงชั้นศาลหรือการสอบสวนทางวินัย หลักฐานต้องพิสูจน์ได้ว่าไม่ถูกแก้**

```bash
# คำนวณ hash ทันทีที่เก็บ แล้วบันทึกไว้
sha256sum evidence.img | tee evidence.img.sha256
```

| ต้องบันทึก | ทำไม |
|---|---|
| ใครเก็บ เมื่อไร จากเครื่องไหน | พิสูจน์ที่มา |
| **hash ตอนเก็บ** | พิสูจน์ว่าไม่ถูกแก้ภายหลัง |
| ใครถือครองต่อ ๆ กัน | ถ้าขาดช่วง หลักฐานใช้ไม่ได้ |
| เก็บที่ไหน เข้าถึงได้โดยใคร | |

**ทำสำเนาแล้ววิเคราะห์จากสำเนาเสมอ ห้ามแตะต้นฉบับ** — และถ้าเป็นเรื่องใหญ่จริง
ให้หยุดแล้วเรียกผู้เชี่ยวชาญ อย่าทำเอง

## 61.3 เก็บหน่วยความจำ {#s61-3}

```bash
# Linux — ต้องลง kernel module ก่อน
sudo insmod lime.ko "path=/mnt/usb/mem.lime format=lime"
```

**เก็บลงสื่อภายนอกเสมอ** ไม่ใช่ดิสก์ของเครื่องที่โดน (จะเขียนทับหลักฐาน)

วิเคราะห์ด้วย **Volatility**:

```bash
vol.py -f mem.lime linux.pslist          # process ที่รันอยู่
vol.py -f mem.lime linux.bash            # ประวัติคำสั่ง bash
vol.py -f mem.lime linux.netstat         # การเชื่อมต่อตอนนั้น
```

**สิ่งที่หาได้จาก RAM แต่หาจากดิสก์ไม่ได้:**

- process ที่ลบไฟล์ตัวเองทิ้งแล้วแต่ยังรันอยู่
- **การเชื่อมต่อไปยัง C2** ที่ปิดไปแล้ว
- คำสั่งที่พิมพ์ · กุญแจเข้ารหัส · รหัสผ่านที่ยังค้างในหน่วยความจำ
- payload ที่ถูก decrypt แล้ว (มัลแวร์เก็บบนดิสก์แบบเข้ารหัสไว้)

## 61.4 เก็บดิสก์ {#s61-4}

```bash
# อ่านอย่างเดียว + hash ไปพร้อมกัน
sudo dd if=/dev/sda bs=4M conv=noerror,sync status=progress | tee disk.img | sha256sum
```

**ใช้ write blocker ถ้ามี** — ป้องกันไม่ให้ระบบเผลอเขียนอะไรลงต้นฉบับ
(แค่ mount ก็เปลี่ยน timestamp ได้แล้ว)

```bash
# ถ้าต้อง mount ให้ mount แบบอ่านอย่างเดียวเสมอ
sudo mount -o ro,noexec,nodev,noload disk.img /mnt/evidence
```

**File carving — กู้ไฟล์ที่ถูกลบ:**

```bash
foremost -i disk.img -o recovered/
```

> **"ลบ" ในระบบไฟล์ส่วนใหญ่คือการลบแค่ *ดัชนี*** ข้อมูลจริงยังอยู่จนกว่าจะถูก
> เขียนทับ — นี่คือเหตุผลที่การลบไฟล์ไม่พอสำหรับข้อมูลอ่อนไหว
> (และเหตุผลที่ต้อง encryption at rest — [บทที่ 58](58-cloud-security.md))

## 61.5 Timeline — หัวใจของการสืบสวน {#s61-5}

**คำถามที่ต้องตอบไม่ใช่ "มีอะไรน่าสงสัยบ้าง" แต่คือ "เกิดอะไรขึ้นตามลำดับ"**

```bash
# สร้าง timeline จากเวลาของไฟล์ทั้งระบบ
fls -r -m / disk.img > bodyfile
mactime -b bodyfile -d > timeline.csv
```

| ตัวย่อ | เวลาอะไร | บอกอะไร |
|---|---|---|
| **M**odified | แก้ไขเนื้อหา | ไฟล์ถูกเขียนเมื่อไร |
| **A**ccessed | เปิดอ่าน | ใครมาอ่าน |
| **C**hanged | metadata เปลี่ยน | สิทธิ์/เจ้าของถูกแก้ |
| **B**irth | สร้าง | ไฟล์มาถึงเครื่องเมื่อไร |

**เทคนิคที่ใช้ได้จริง: หาไฟล์ที่ถูกสร้างในช่วงเวลาที่สงสัย**

```bash
# ไฟล์ที่เปลี่ยนใน 2 วันที่ผ่านมา ในที่ที่ไม่ควรมีอะไรเปลี่ยน
sudo find /etc /usr/bin /usr/sbin -mtime -2 -type f
```

> ## ⚠️ เวลาโกหกได้
>
> ผู้โจมตีที่มีความรู้จะ **timestomp** — แก้เวลาไฟล์ให้ดูเหมือนของเก่า
>
> **แต่แก้ได้ไม่ครบทุกตัว** — บางระบบไฟล์เก็บเวลาไว้หลายที่ (`$STANDARD_INFORMATION`
> vs `$FILE_NAME` ใน NTFS) ถ้าสองค่าไม่ตรงกัน นั่นคือสัญญาณว่ามีการแก้เวลา
>
> และ**เวลาของเครื่องอื่นในเครือข่ายก็ยังใช้เทียบได้** — นี่คือเหตุผลที่
> คลัสเตอร์ต้องมี NTP ตรงกันทุกโหนด

## 61.6 หลักฐานที่หาง่ายที่สุดบน Linux {#s61-6}

เริ่มจากที่เหล่านี้ก่อน — ได้ผลเร็วและไม่ต้องใช้เครื่องมือพิเศษ

| ที่ | หาอะไร |
|---|---|
| `/var/log/auth.log` | **การ login สำเร็จ/ล้มเหลว · การใช้ sudo** |
| `~/.bash_history` | คำสั่งที่พิมพ์ (⚠️ ลบง่าย ไม่มีเวลากำกับ) |
| `/etc/passwd`, `/etc/shadow` | บัญชีที่ถูกเพิ่มใหม่ |
| `crontab -l`, `/etc/cron.*` | **persistence** ([บทที่ 39](39-how-malware-works.md)) |
| `systemctl list-units` | service แปลกปลอม |
| `~/.ssh/authorized_keys` | 🔴 **กุญแจที่ถูกเพิ่มเข้ามา** |
| `/var/log/wtmp` (`last`) | ใครล็อกอินจากไหน เมื่อไร |

```bash
# ชุดคำสั่งเริ่มต้นเมื่อสงสัยว่าเครื่องถูกยึด
last -20                                    # ใครเข้ามาล่าสุด
grep -i 'accepted\|failed' /var/log/auth.log | tail -30
sudo find / -name authorized_keys -newermt '-7 days' 2>/dev/null
sudo find /etc/cron* /etc/systemd -mtime -7 2>/dev/null
```

**`authorized_keys` ที่ถูกเพิ่มคือสิ่งที่ควรตรวจก่อนเสมอ** — มันคือวิธี
คงสิทธิ์เข้าถึงที่ง่ายที่สุดและถูกใช้บ่อยที่สุด และเป็นเหตุผลที่คลัสเตอร์
ควรเฝ้าไฟล์นี้ทุกโหนด

## 61.7 ห้องแล็บสำหรับฝึก {#s61-7}

**อย่าฝึกกับเครื่องจริงที่เกิดเหตุ** — สร้างเหตุการณ์เองใน VM ([บทที่ 45](45-home-lab.md))

```
1. สร้าง VM แล้ว snapshot ไว้
2. จำลองการถูกเจาะ: เพิ่ม user · ใส่ cron · เพิ่ม authorized_keys
3. snapshot อีกครั้ง
4. ให้ตัวเอง (หรือเพื่อน) สืบว่าเกิดอะไรขึ้นโดยดูจากหลักฐานอย่างเดียว
5. เทียบกับสิ่งที่ทำจริง — พลาดข้อไหนไปบ้าง
```

**ขั้นที่ 5 คือส่วนที่สอนมากที่สุด** — คุณจะพบว่าร่องรอยที่คิดว่าชัดเจน
กลับหาไม่เจอ และร่องรอยที่ไม่ได้ตั้งใจทิ้งไว้กลับเป็นตัวที่ชี้ชัดที่สุด

## แบบฝึกหัด

1. สร้าง timeline ของโฟลเดอร์ `/etc` ในเครื่องคุณ — ไฟล์ไหนถูกแก้ล่าสุด ทำไม
2. `grep` หา login ที่ล้มเหลวใน `auth.log` — มีการพยายามเดารหัสไหม
3. ตรวจ `authorized_keys` ทุกบัญชีในเครื่อง — มีกุญแจที่คุณจำไม่ได้ไหม
4. ลบไฟล์แล้วกู้ด้วย `foremost` — กู้ได้ไหม แล้วถ้าเขียนทับก่อนล่ะ
5. ทำแล็บในข้อ [61.7](#s61-7) แล้วเขียนรายงานว่า "เข้ามาทางไหน ทำอะไรไป"
6. ตอบตัวเอง: ถ้าเซิร์ฟเวอร์ของคุณถูกยึดตอนนี้ **หลักฐานอะไรที่ยังมีอยู่**
   และอะไรที่หายไปแล้วเพราะไม่ได้เก็บ log ไว้
7. คิดจากข้อ 6 ย้อนกลับ: ต้องเปิด log อะไรเพิ่มตั้งแต่วันนี้ ([บทที่ 28](28-observability-and-deployment.md))

# บทที่ 63 · Reverse engineering เบื้องต้น

> [บทที่ 40](40-malware-analysis-basics.md) วิเคราะห์มัลแวร์จากพฤติกรรม **บทนี้ลงไปอีกชั้น —
> อ่านว่าโปรแกรมทำอะไรจากตัวมันเอง โดยไม่มีซอร์สโค้ด**
>
> ทุกอย่างในบทนี้ทำกับ binary ที่เราสร้างเอง รันได้จริงใน [lab/re/](../lab/re/)

## 63.1 ทำไมต้องอ่านโปรแกรมที่ไม่มีซอร์ส {#s63-1}

| สถานการณ์ | ทำไมต้อง RE |
|---|---|
| วิเคราะห์มัลแวร์ | เจ้าของไม่ได้แจกซอร์สให้ ([บทที่ 39](39-how-malware-works.md)) |
| หาช่องโหว่ในโปรแกรมปิด | ไม่มีโค้ดให้อ่าน |
| เข้าใจ protocol ของแอปมือถือ | ต่อยอดจาก[บทที่ 19](19-mitmproxy-mobile-traffic.md) |
| CTF หมวด reverse/pwn | ([บทที่ 44](44-ctf-and-legal-practice.md)) |
| ตรวจว่า binary ที่ได้มาทำอะไรจริง | supply chain ([บทที่ 42](42-supply-chain-security.md)) |

**ทักษะนี้ต่อยอดจาก[บทที่ 37](37-memory-and-classic-exploits.md) โดยตรง** — บทนั้นอธิบายว่าโปรแกรมอยู่ในหน่วยความจำ
อย่างไร บทนี้อ่านคำสั่งที่ CPU รันจริง

## 63.2 จากซอร์สถึงสิ่งที่ CPU เห็น {#s63-2}

```
โค้ด C  →  [compiler]  →  assembly  →  [assembler]  →  machine code (ไบต์)
                                                          ↑
                                          นี่คือสิ่งที่อยู่ในไฟล์ .exe/.so
```

**reverse engineering คือการเดินย้อนทาง** — จากไบต์ กลับไปเข้าใจตรรกะ
โดยที่**คอมเมนต์ ชื่อตัวแปร และโครงสร้างเดิมหายไปหมดแล้ว**

โจทย์ของเราใน `lab/re/crackme.c`:

```c
int check(const char *pw) {
    return strcmp(pw, "s3cr3t") == 0;
}
```

คอมไพล์แบบที่อ่านง่ายที่สุดก่อน (ยังไม่ optimize, ไม่สุ่มตำแหน่ง):

```bash
gcc -O0 -no-pie -o crackme crackme.c
```

## 63.3 เริ่มจากที่ง่ายที่สุดเสมอ — `strings` {#s63-3}

**ก่อนแตะ disassembler ให้ลองสิ่งที่ใช้ 2 วินาทีก่อน**

```bash
strings crackme | grep s3
```

```
s3cr3t
```

**รหัสผ่านโผล่มาตรง ๆ** — เพราะมันเป็น string ธรรมดาที่ฝังในไฟล์
ไม่ได้เข้ารหัสอะไร

> ## นี่คือบทเรียนความปลอดภัยที่สำคัญที่สุดของทั้งบท
>
> **อย่าฝังความลับไว้ใน binary** — API key, รหัสผ่าน, endpoint ลับ
> ทั้งหมดนี้ `strings` ดึงออกมาได้ในคำสั่งเดียว
>
> "ผู้ใช้มองไม่เห็นโค้ด" ไม่เท่ากับ "ผู้ใช้หาความลับไม่เจอ" — นี่คือเหตุผล
> ที่[บทที่ 7](07-tls-https.md) เรื่อง cert pinning ต้องมี backup pin และเหตุผลที่
> mobile app ห้ามเก็บ secret ไว้ในตัวแอป ([บทที่ 11](11-mobile-api-auth-design.md))

**มัลแวร์จริงมักบีบอัดหรือเข้ารหัส string ของตัวเอง** (packing) เพื่อกัน
`strings` — ถ้า `strings` ให้ผลน้อยผิดปกติ นั่นเองคือสัญญาณ ([บทที่ 40](40-malware-analysis-basics.md))

## 63.4 อ่าน assembly — ไม่ต้องเข้าใจทุกบรรทัด {#s63-4}

```bash
objdump -d --no-show-raw-insn crackme
```

ฟังก์ชัน `check` ที่ CPU รันจริง:

```asm
0000000000401176 <check>:
  push   %rbp                      ; เปิดฟังก์ชัน (บทที่ 37 — stack frame)
  mov    %rsp,%rbp
  sub    $0x10,%rsp
  mov    %rdi,-0x8(%rbp)           ; เก็บ argument แรก (pw)
  ...
  lea    0xe77(%rip),%rdx          ; โหลดที่อยู่ของ "s3cr3t"
  mov    %rdx,%rsi                 ; arg 2 ของ strcmp
  mov    %rax,%rdi                 ; arg 1 = pw
  call   401080 <strcmp@plt>       ; เรียก strcmp(pw, "s3cr3t")
  test   %eax,%eax                 ; ผลเป็น 0 ไหม (0 = เท่ากัน)
  sete   %al                       ; ถ้าเท่ากัน al = 1
  ...
  ret
```

**ไม่ต้องอ่านออกทุกบรรทัด — จับแค่ 3 จุดพอ:**

| มองหา | เพราะ |
|---|---|
| `call ...@plt` | เรียกฟังก์ชันอะไร (`strcmp`, `system`, `memcpy`...) |
| `lea ...` ที่ตามด้วยที่อยู่ string | ข้อมูลคงที่ที่โปรแกรมใช้ |
| **`test`/`cmp` + `je`/`jne`/`sete`** | 🎯 **จุดตัดสินใจ** — นี่คือที่ที่ตรรกะอยู่ |

**จุดที่สามคือหัวใจ** — `test %eax,%eax` แล้ว `sete` คือการถาม
"strcmp คืน 0 ไหม" ทั้งความมั่นคงของโปรแกรมนี้อยู่ที่คำสั่งเดียวนี้

## 63.5 register และคำสั่งที่เจอบ่อย {#s63-5}

พอสำหรับอ่าน crackme ทั่วไป — ไม่ต้องท่องทั้งชุด

| register | ใช้ทำอะไร (x86-64 System V) |
|---|---|
| `rdi, rsi, rdx, rcx, r8, r9` | **argument ที่ 1-6** ของฟังก์ชัน |
| `rax` | **ค่าที่ return** |
| `rbp, rsp` | ฐานและยอดของ stack ([บทที่ 37](37-memory-and-classic-exploits.md)) |
| `rip` | คำสั่งถัดไปที่จะรัน |

| คำสั่ง | ทำอะไร |
|---|---|
| `mov a, b` | คัดลอก b ไป a |
| `lea a, b` | เอา**ที่อยู่**ของ b (ไม่ใช่ค่า) |
| `call` / `ret` | เรียก / คืนจากฟังก์ชัน |
| `cmp` / `test` | เทียบค่า (ตั้ง flag) |
| **`je`/`jne`/`jz`/`jnz`** | **กระโดดตามเงื่อนไข** ← ตรรกะอยู่ที่นี่ |

## 63.6 แก้ binary ด้วยการพลิก 1 ไบต์ {#s63-6}

ตรรกะทั้งหมดของ `check` อยู่ที่คำสั่ง `sete` — ถ้าเปลี่ยนเป็น `setne`
ผลจะกลับด้าน **รหัสถูกกลายเป็นไม่ผ่าน รหัสผิดกลายเป็นผ่าน**

```
sete  %al  =  0f 94 c0
setne %al  =  0f 95 c0
              ─────┬
              ต่างกันไบต์เดียว: 94 → 95
```

```python
data = bytearray(open("crackme", "rb").read())
i = data.find(bytes.fromhex("0f94c0"))     # หา sete
data[i + 1] = 0x95                          # เปลี่ยนเป็น setne
open("crackme_patched", "wb").write(data)
```

ผลจริง (`make demo` ใน [lab/re/](../lab/re/)):

```
=== รันปกติ ===
./crackme s3cr3t   → ผ่าน       exit=0
./crackme wrong    → ไม่ผ่าน     exit=1

=== หลังแก้ 1 ไบต์ ===
./crackme_patched wrong → ผ่าน   exit=0   ← รหัสผิดกลับผ่าน
```

> ## นี่คือเหตุผลที่การตรวจสิทธิ์ฝั่ง client เชื่อถือไม่ได้เลย
>
> ถ้าโปรแกรมตัดสินใจเรื่องสำคัญ (จ่ายเงินแล้วหรือยัง, เป็นสมาชิกพรีเมียมไหม)
> **ด้วยโค้ดที่รันบนเครื่องของผู้ใช้** ผู้ใช้พลิกผลได้ด้วยการแก้ไบต์เดียว
>
> เป็นหลักการเดียวกับ[บทที่ 24](24-authorization-and-bola.md): **การตัดสินใจเรื่องสิทธิ์ต้องเกิด
> ฝั่ง server ที่ผู้ใช้แตะไม่ได้** — client ที่ผู้ใช้ควบคุมได้ ไม่ใช่ที่ที่
> วางความไว้ใจ ([บทที่ 63.3](#s63-3) เพิ่งแสดงว่าเขาอ่านได้ ข้อนี้แสดงว่าเขาแก้ได้)

## 63.7 ดูตอนมันรันจริงด้วย gdb {#s63-7}

static analysis (อ่านโดยไม่รัน) บอกได้เยอะ แต่บางอย่างต้องดูตอนรัน
โดยเฉพาะโปรแกรมที่ decrypt ตัวเองหรือคำนวณค่าตอน runtime

```bash
gdb ./crackme
(gdb) break strcmp          # หยุดตอนจะเทียบ string
(gdb) run mypassword
(gdb) x/s $rsi              # ดู argument ที่ 2 = string ที่ถูกเทียบด้วย
0x402008: "s3cr3t"          ← เห็นรหัสจริงตอน runtime
```

**เทคนิคนี้ชนะ packing** — ต่อให้ string ถูกเข้ารหัสในไฟล์ พอโปรแกรมจะใช้
มันต้อง decrypt ในหน่วยความจำก่อน แล้วเราดักดูตรงนั้นได้ (ต่อยอดจาก
`strace`/`ltrace` ใน[บทที่ 35](35-linux-internals.md))

| คำสั่ง gdb | ทำอะไร |
|---|---|
| `break <ที่>` | ตั้งจุดหยุด |
| `run <args>` | เริ่มรัน |
| `x/s $reg` | ดู string ที่ register ชี้ไป |
| `info registers` | ดูค่า register ทั้งหมด |
| `stepi` / `nexti` | เดินทีละคำสั่ง |

## 63.8 เครื่องมือระดับถัดไป {#s63-8}

เมื่อ objdump เริ่มไม่พอ (โปรแกรมใหญ่ ต้องดูภาพรวม)

| เครื่องมือ | จุดเด่น | ราคา |
|---|---|---|
| **Ghidra** | แปลง assembly กลับเป็น C ให้อ่าน (decompiler) · ของ NSA | ฟรี |
| **radare2 / rizin** | ครบเครื่องใน terminal | ฟรี |
| **Binary Ninja** | UI ดี decompiler ดี | จ่าย (มีรุ่นฟรี) |
| IDA Pro | มาตรฐานอุตสาหกรรม | แพงมาก |

> **เริ่มที่ Ghidra** — decompiler ของมันเปลี่ยน assembly ยาว ๆ กลับเป็น
> โค้ดคล้าย C ที่อ่านเข้าใจได้เร็วกว่ามาก และฟรีเต็มรูปแบบ
>
> แต่**อย่าข้ามการอ่าน assembly เอง** — decompiler เดาผิดได้ และตอน
> decompiler สับสน (โค้ดที่จงใจทำให้งง) คุณต้องกลับมาอ่าน assembly อยู่ดี

## 63.9 ขอบเขต {#s63-9}

- ✅ แกะ binary ที่คุณสร้างเอง / crackme สำหรับฝึก / มัลแวร์ในแล็บของตัวเอง
- ✅ วิเคราะห์มัลแวร์เพื่อป้องกัน ([บทที่ 40](40-malware-analysis-basics.md) — ทำใน VM ที่แยกขาด)
- ⚠️ ซอฟต์แวร์เชิงพาณิชย์มักมี EULA ห้าม RE — อ่านก่อน
- 🔴 แกะเพื่อ crack license / ละเมิดลิขสิทธิ์ — ผิดกฎหมาย

**การเข้าใจกลไกเป็นสิ่งที่ควรรู้ การเอาไปละเมิดสิทธิ์ผู้อื่นเป็นคนละเรื่อง**
([บทที่ 22](22-ethics-and-limits.md))

## แบบฝึกหัด

1. `make demo` ใน [lab/re/](../lab/re/) แล้วอ่านว่าแต่ละขั้นทำอะไร
2. `strings` binary อื่นในเครื่อง — เจอ path, URL, หรือข้อความอะไรบ้าง
3. เปิด `crackme` ใน `objdump -d` แล้วหา `call ...@plt` ทั้งหมด — เรียกอะไรบ้าง
4. ใช้ gdb ตั้ง breakpoint ที่ `strcmp` แล้วดูรหัสจริง (ข้อ [63.7](#s63-7))
5. แก้ `patch.py` ให้พลิกที่ `je`/`jne` ใน `main` แทน — ได้ผลเหมือนกันไหม
6. คอมไพล์ใหม่ด้วย `-O2` แล้วเทียบ assembly — ต่างจาก `-O0` อย่างไร ทำไมอ่านยากขึ้น
7. ตอบตัวเอง: โปรแกรมของคุณมีการตัดสินใจเรื่องสิทธิ์ฝั่ง client ตรงไหนบ้าง
   ([บทที่ 63.6](#s63-6)) — ย้ายไป server ได้ไหม
8. ลง Ghidra แล้วเปิด `crackme` — decompiler แปลง `check` กลับเป็น C
   ได้ใกล้ของจริงแค่ไหน

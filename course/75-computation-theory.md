# บทที่ 75 · ทฤษฎีการคำนวณภาคปฏิบัติ — ส่วนที่เปลี่ยนการตัดสินใจ

> มีคนบอกว่า "programmer เก่งต้องรู้ทฤษฎีการคำนวณ" — **จริงครึ่งเดียว**
>
> บทนี้เอาเฉพาะส่วนที่**เปลี่ยนวิธีตัดสินใจจริง**: Big-O ที่แปลงเป็นเวลาบน
> นาฬิกาได้, การรู้ว่าปัญหาไหนแก้ไม่ได้เลย — ข้ามการพิสูจน์เชิงรูปนัยที่เป็น
> ของนักวิจัย
>
> ทุกตัวเลขวัดจริงด้วย [lab/bigo_demo.py](../lab/bigo_demo.py)

## 75.1 Big-O คืออะไร — และทำไมมันไม่ใช่ "ความเร็ว" {#s75-1}

```
Big-O = เวลาโตขึ้นอย่างไรเมื่อข้อมูลโตขึ้น  (ไม่ใช่เวลาสัมบูรณ์)
```

| Big-O | ชื่อ | ข้อมูลโต 10 เท่า เวลาโต |
|---|---|---|
| **O(1)** | คงที่ | เท่าเดิม |
| **O(log n)** | ลอการิทึม | +นิดเดียว |
| **O(n)** | เชิงเส้น | 10 เท่า |
| **O(n log n)** | | ~13 เท่า |
| **O(n²)** | กำลังสอง | **100 เท่า** |
| **O(2ⁿ)** | เอกซ์โพเนนเชียล | 🔴 พังทันทีที่ n โตนิดเดียว |

> **Big-O บอก "แนวโน้ม" ไม่ใช่ "เร็วช้าตอนนี้"** — โค้ด O(n²) อาจเร็วกว่า O(n)
> ตอน n เล็ก แต่พอ n โต O(n²) แพ้ยับเสมอ **ปัญหา performance ที่โผล่ตอน scale
> คือ Big-O ที่ผิด ไม่ใช่โค้ดที่เขียนไม่ดี**

## 75.2 พิสูจน์ว่า Big-O ไม่ใช่ทฤษฎีลอย ๆ {#s75-2}

[บทที่ 27](27-database-and-performance.md) วัด index (O(log n)) เร็วกว่า scan (O(n)) ได้ 271 เท่า
บทนี้วัดในโค้ด Python ตรง ๆ

**ค้นหาสมาชิก: `in list` เป็น O(n) · `in set` เป็น O(1)**

```python
x in data_list      # ต้องไล่ทีละตัว = O(n)
x in data_set       # hash ตรงไปเลย = O(1)
```

วัดจริง (ค้นหา 1000 ครั้ง):

```
      ขนาด    list (ms)     set (ms)   เร็วกว่า
      1000         2.72       0.0278        98x
     10000        23.82       0.0346       688x
    100000       226.67       0.1237      1833x
```

> ## สังเกตว่า "เร็วกว่า" โตขึ้นเรื่อย ๆ — นี่คือหัวใจ
>
> 98x → 688x → **1833x** ยิ่งข้อมูลใหญ่ยิ่งต่างมาก **นี่คือความหมายจริงของ
> "Big-O ต่างกัน"** — ไม่ใช่ set เร็วกว่าคงที่ แต่ช่องว่าง**ขยายตาม n**
>
> ถ้าเป็นแค่ค่าคงที่ (เช่น 2 เท่าตลอด) นั่นคือ Big-O เท่ากัน ต่างแค่ค่าคงที่ —
> เรื่องเล็ก แต่ Big-O ต่างกันคือเรื่องใหญ่ที่ทำให้ระบบพังตอน scale

**เปลี่ยน `list` เป็น `set`/`dict` บรรทัดเดียว = เร็วขึ้นหลักพันเท่าตอนข้อมูลใหญ่**
— นี่คือ optimization ที่ profiler ([บทที่ 67](67-profiling.md)) ชี้บ่อยที่สุด

## 75.3 O(n²) — กับดักที่ซ่อนใน loop ซ้อน {#s75-3}

```python
# หาคู่ซ้ำ — loop ซ้อน = O(n²)
for i in range(len(a)):
    for j in range(i+1, len(a)):
        if a[i] == a[j]: ...
```

วัดจริง เทียบกับวิธี O(n) (`len(set(a)) != len(a)`):

```
      ขนาด     O(n²) (ms)    O(n) (ms)   เร็วกว่า
       500           2.57       0.0085       301x
      1000          10.97       0.0100      1098x
      2000          45.45       0.0448      1015x
```

**ข้อมูลโต 2 เท่า (1000→2000) เวลา O(n²) โต ~4 เท่า** (10.97→45.45) — นั่นคือ
ลายเซ็นของ n² และเป็นเหตุผลที่โค้ดนี้ใช้ได้ตอนทดสอบ (n เล็ก) แล้วพังตอน
production (n ใหญ่)

> **loop ซ้อนบน collection เดียวกันคือธงแดง** — เจอเมื่อไรถามทันทีว่า
> "มีวิธี O(n) ด้วย hash ไหม" มักมี

## 75.4 โครงสร้างข้อมูล = เลือก Big-O {#s75-4}

**การเลือกโครงสร้างข้อมูลคือการเลือก Big-O ของ operation ที่ทำบ่อย**

| ต้องการ | ใช้ | ค้นหา | เพิ่ม |
|---|---|---|---|
| ค้นหาบ่อย | **set / dict** | O(1) | O(1) |
| เรียงลำดับ + ค้นหา | list ที่ sort แล้ว (binary search) | O(log n) | O(n) |
| เข้า-ออกหัวท้าย | **deque** | — | O(1) |
| ลำดับความสำคัญ | **heap** | — | O(log n) |
| ต่อท้ายบ่อย | list | — | O(1) เฉลี่ย |

```python
# ❌ เช็คซ้ำใน list ที่โตเรื่อย ๆ = O(n²) รวม
seen = []
for x in data:
    if x not in seen:        # O(n) ทุกรอบ
        seen.append(x)

# ✅ ใช้ set = O(n) รวม
seen = set()
for x in data:
    if x not in seen:        # O(1)
        seen.add(x)
```

> **บั๊ก performance อันดับหนึ่งใน Python คือ `x in list` ใน loop** — ดูไม่ผิด
> แต่เป็น O(n²) ซ่อนอยู่ เปลี่ยนเป็น set แก้ได้ทันที (profiler บทที่ 67 ชี้จุดนี้ได้)

## 75.5 P vs NP — รู้ว่าปัญหาไหน "แก้สมบูรณ์แบบไม่ได้" {#s75-5}

บาง**ปัญหาไม่มีวิธีเร็ว** — ไม่ใช่เพราะยังไม่มีใครคิดออก แต่เชื่อกันว่า
**ไม่มีจริง ๆ**

| กลุ่ม | คือ | ตัวอย่าง |
|---|---|---|
| **P** | แก้ได้ในเวลา polynomial (เร็วพอใช้) | เรียงลำดับ, ค้นหา, shortest path |
| **NP-complete** | ตรวจคำตอบเร็ว แต่**หาคำตอบช้ามาก** | จัดตารางที่ดีที่สุด, bin packing, TSP |

**ทำไมต้องรู้:** ถ้าปัญหาที่เจอเป็น NP-complete **เลิกพยายามหาคำตอบที่สมบูรณ์แบบ**
— ไปใช้ heuristic (คำตอบที่ดีพอ ไม่ใช่ดีที่สุด) แทน

```
❌ พยายามหาตารางเวลาที่ดีที่สุดของ 500 งาน  → รันเป็นล้านปี
✅ ใช้ heuristic ได้ตารางที่ดี 95%           → รันเสร็จใน 1 วินาที
```

> ## เรื่องนี้โผล่ในเล่มนี้แล้วโดยไม่ได้เรียกชื่อ
>
> - **GPU scheduling** ([บทที่ 49](49-gpu-on-containers-and-k8s.md)) — จัดสรรที่ดีที่สุดเป็น NP-hard
>   จริง Slurm/HAMi จึงใช้ heuristic (binpack, spread) ไม่ใช่คำตอบที่สมบูรณ์
> - **Cryptography** ([บทที่ 38](38-crypto-in-practice.md)) — **ความปลอดภัยตั้งอยู่บนความยาก**
>   การแยกตัวประกอบเลขใหญ่ยาก (เชื่อว่าไม่อยู่ใน P) จึงถอดรหัสไม่ได้ในเวลาที่
>   มีความหมาย **ถ้า P=NP ครุ่นวันหนึ่ง crypto ทั้งโลกพัง**
>
> **นี่คือ computation theory ที่คุณพึ่งพาอยู่ทุกวัน** — ไม่ใช่ทฤษฎีในตำรา

## 75.6 Undecidable — บางอย่างพิสูจน์แล้วว่าทำไม่ได้เลย {#s75-6}

ต่างจาก NP (ช้ามาก) — **undecidable คือ "ไม่มีโปรแกรมไหนทำได้ ไม่ว่านานแค่ไหน"**

**Halting problem:** เขียนโปรแกรมที่รับโปรแกรมอื่นมา แล้วบอกได้ว่ามันจะ**หยุด
หรือวนไม่รู้จบ** — พิสูจน์แล้วว่า**เป็นไปไม่ได้** สำหรับทุกกรณี

> ## ทำไมเรื่องนี้สำคัญกับงานจริง
>
> **ความสมบูรณ์แบบบางอย่างเป็นไปไม่ได้เชิงทฤษฎี ไม่ใช่แค่ยาก:**
>
> - **antivirus ที่จับมัลแวร์ได้ครบ 100%** ([บทที่ 40](40-malware-analysis-basics.md)) — เป็นไปไม่ได้
>   เพราะลดรูปเป็น halting problem ได้ จึงต้องพึ่ง signature + heuristic เสมอ
> - **static analyzer ที่หาบั๊กได้ครบทุกตัว** — เป็นไปไม่ได้ด้วยเหตุผลเดียวกัน
> - **ตัวตรวจว่าโค้ดสองอันทำงานเหมือนกันไหม** — undecidable
>
> **รู้ข้อนี้แล้วจะเลิกตามหาเครื่องมือที่ "จับได้ทุกอย่าง"** — มันไม่มีจริง
> เป้าหมายที่ถูกคือ "จับได้มากพอที่จะคุ้ม" ไม่ใช่ "จับได้ครบ"

## 75.7 สรุป — ทฤษฎีเท่าไรถึงพอ {#s75-7}

| เรื่อง | คุ้มแค่ไหน | ใช้ตอน |
|---|---|---|
| **Big-O + โครงสร้างข้อมูล** | 🟢 ใช้ทุกวัน | เขียนโค้ดทุกครั้ง |
| รู้ว่าปัญหาเป็น NP | 🟡 เปลี่ยนการตัดสินใจ | เจอปัญหา optimize/scheduling |
| รู้ว่าบางอย่าง undecidable | 🟡 เลิกตามหาสิ่งที่ไม่มี | ประเมินเครื่องมือ security |
| linear algebra + probability | 🟢 **สำคัญมากสำหรับ ML** | ทุกอย่างใน data science |
| การพิสูจน์เชิงรูปนัย, Turing machine | 🔴 ไม่จำเป็น | งานวิจัย |

> **คำ claim ที่ว่า "ไม่รู้ทฤษฎีไม่ได้" ถูกครึ่งเดียว** — Big-O และการรู้ขีดจำกัด
> **ทำให้เพดานความสามารถสูงขึ้นจริง** และเปลี่ยนวิธีคิดปัญหา
>
> แต่มันเป็น "รู้แล้วเก่งขึ้น" ไม่ใช่ "ไม่รู้แล้วทำงานไม่ได้" — developer เก่ง
> จำนวนมากเรียนเท่าที่งานต้องใช้ แล้วลงลึกเมื่อเจอปัญหาที่ต้องใช้จริง
>
> **สำหรับสาย data science: Big-O + linear algebra + probability คือสามเรื่อง
> ที่คุ้มที่สุด** — ML ทั้งวงการตั้งอยู่บนสามอย่างนี้

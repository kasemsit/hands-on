# บทที่ 82 · ประเมินผลโมเดล LLM — วัดให้เป็น debug ให้เป็น

> [บทที่ 51](51-gpu-observability-and-cost.md) วัดว่า serve เร็วแค่ไหน **บทนี้วัดอีกด้าน: โมเดลตอบ
> ถูกแค่ไหน** — และทักษะที่สำคัญกว่าการรัน benchmark คือ **debug คะแนนเป็น**
>
> ตัวอย่าง debug รันจริงด้วย [lab/eval_debug_demo.py](../lab/eval_debug_demo.py)

## 82.1 ทำไมต้องวัด — "รู้สึกว่าดีขึ้น" ไม่พอ {#s82-1}

```
เปลี่ยนโมเดล / quantize / แก้ prompt → ดีขึ้นหรือแย่ลง?
   "รู้สึกว่าดีขึ้น"  →  วัดไม่ได้ เทียบไม่ได้ ตัดสินใจไม่ได้
   benchmark คะแนน   →  ตัวเลขที่เทียบได้
```

**เป็นหลักการเดียวกับ profiling ([บทที่ 67](67-profiling.md)) และ MLOps ([บทที่ 72.6](72-mlops.md#s72-6))** — ต้องมี
เกณฑ์ที่วัดได้ ไม่ใช่ความรู้สึก โดยเฉพาะตอนเปลี่ยน kernel/precision ([บทที่ 66](66-training-and-finetuning.md))
ต้องพิสูจน์ว่าไม่ทำให้แย่ลง

## 82.2 benchmark ยอดนิยมวัดอะไร {#s82-2}

```
GSM8K          เลข/reasoning ระดับประถม
GPQA-Diamond   วิทยาศาสตร์ระดับปริญญาเอก
OCRBench       อ่านตัวอักษรจากภาพ
MMMU           เข้าใจภาพ+ข้อความหลายสาขา
```

| benchmark | วัดอะไร | ใช้เทียบเมื่อ |
|---|---|---|
| **GSM8K** | คณิต/reasoning | โมเดลคิดเลข/logic ได้ไหม |
| **GPQA-Diamond** | ความรู้ลึกระดับ PhD | โมเดลเก่งจริงหรือจำมา |
| **OCRBench** | อ่านภาพ | โมเดล vision ([บทที่ 81.5](81-serving-features.md#s81-5)) |
| **MMMU** | multimodal หลายสาขา | vision + reasoning |

> **เลือก benchmark ให้ตรงกับงานจริง** — โมเดลที่ได้ GSM8K สูงไม่ได้แปลว่าเก่ง
> OCR ถ้างานคุณคืออ่านเอกสาร ดู OCRBench ไม่ใช่ GSM8K

## 82.3 🔴 debug คะแนน — "ตอบผิด" หรือ "โดนตัด" {#s82-3}

**นี่คือทักษะที่สำคัญกว่าการรัน benchmark** — คะแนนต่ำไม่ได้แปลว่าโมเดลโง่

วัดจริง — 3 เคส:

```
expected     got    finish  วินิจฉัย
     345     345  finished  ✅ ถูก
     345       ?    length  ⚠️ โดนตัด! (เพิ่ม max_tokens ไม่ใช่โทษโมเดล)
     144       ?  finished  🔴 ตอบผิดจริง
```

**เคสกลางคือกับดัก** — โมเดลกำลังคิดถูก (`15*23 = 300 +...`) แต่ output ถูกตัด
เพราะชน `max_tokens` **คะแนนตกเพราะตั้งค่า serve ผิด ไม่ใช่โมเดลผิด**

| `finish_reason` | แปลว่า | ทำอะไร |
|---|---|---|
| `stop` / finished | โมเดลจบเอง | ถ้าผิด = ผิดจริง |
| **`length`** | ชน max_tokens | 🔴 **เพิ่ม max_tokens แล้ววัดใหม่** |
| `content_filter` | ถูกกรอง | ตรวจ filter |

> ## เช็ค `finish_reason` ก่อนโทษโมเดลเสมอ
>
> คะแนน eval ตกเพราะ `max_tokens` สั้นไปเป็นเรื่องที่เจอบ่อยมาก — โดยเฉพาะ
> โมเดล reasoning ([บทที่ 81.4](81-serving-features.md#s81-4)) ที่คิดยาวก่อนตอบ ถ้า max_tokens สั้น
> มันถูกตัดกลางความคิด **ดู finish_reason ก่อน แล้วค่อยสรุปว่าโมเดลตอบผิด**

## 82.4 กับดักอื่นของการวัด {#s82-4}

| กับดัก | ผล |
|---|---|
| **parsing คำตอบผิด** | โมเดลตอบ "345 บาท" แต่ regex หาแค่ "345" ไม่เจอ |
| prompt format ต่าง | few-shot format ต่างกันคะแนนต่างกันมาก |
| **contamination** | โมเดลเคยเห็น test set ตอน train → คะแนนสูงปลอม |
| temperature ไม่ 0 | สุ่ม → วัดซ้ำได้คนละคะแนน ([บทที่ 72.2](72-mlops.md#s72-2)) |
| chat template ผิด | โมเดลตอบเพี้ยน ([บทที่ 81.1](81-serving-features.md#s81-1)) |

> **ตั้ง temperature = 0 ตอน eval** เพื่อให้ reproduce ได้ ([บทที่ 72.2](72-mlops.md#s72-2)) —
> ไม่งั้นวัดสองครั้งได้คนละคะแนน แยกไม่ออกว่าที่ต่างเพราะการเปลี่ยนแปลง
> หรือเพราะความสุ่ม

## 82.5 numerical correctness — หลังเปลี่ยน kernel/precision {#s82-5}

ต่อจาก[บทที่ 66](66-training-and-finetuning.md) — เมื่อเปลี่ยน quantization (FP8/int4) หรือ kernel
ต้องพิสูจน์ว่า output ยังถูก

```
1. รัน benchmark ก่อนเปลี่ยน → คะแนนฐาน
2. เปลี่ยน (quantize / kernel ใหม่)
3. รันซ้ำ → คะแนนตกไหม
```

| ตรวจอะไร | ยังไง |
|---|---|
| output เหมือนเดิมไหม | เทียบ logit / token กับ baseline |
| คะแนน benchmark ตกไหม | GSM8K ก่อน/หลัง |
| **เคสขอบ** | ตัวเลขใหญ่, context ยาว ที่ precision ต่ำอาจเพี้ยน |

> **quantize แล้วคะแนนตกนิดหน่อยเป็นเรื่องปกติ ต้องชั่งกับ VRAM ที่ประหยัด** —
> int4 อาจตก 1-2% แต่ประหยัด VRAM 4 เท่า ([บทที่ 47.8](47-gpu-memory-and-kv-cache.md#s47-8)) คุ้มไหมขึ้นกับงาน
> **แต่ต้องวัด ไม่ใช่เดา**

## 82.6 ออกแบบการทดลองให้ reproduce ได้ {#s82-6}

ต่อจาก MLOps ([บทที่ 72.3](72-mlops.md#s72-3)) — eval ที่ทำซ้ำไม่ได้ = เชื่อไม่ได้

**ต้องบันทึกให้ครบ:**

- [ ] โมเดล + version + quantization
- [ ] benchmark + version (test set เปลี่ยนได้)
- [ ] **flag/env var ทั้งหมด** ที่ใช้ serve
- [ ] hardware (การ์ดต่างผลต่างได้ในเคส precision ต่ำ)
- [ ] temperature, max_tokens, prompt template
- [ ] `finish_reason` distribution (กี่ % โดนตัด)

> **"คะแนน 82%" ไม่มีความหมายถ้าไม่บอกว่าวัดยังไง** — บล็อก/paper ที่ดี
> ระบุ flag ครบให้ทำซ้ำได้ นี่คือส่วนหนึ่งของทักษะการสื่อสาร ([บทที่ 68](68-observability-deep.md),
> และเป็น requirement ข้อ 11 ของงาน serving)

## แบบฝึกหัด

1. รัน [lab/eval_debug_demo.py](../lab/eval_debug_demo.py) — เคสไหน "โดนตัด" ไม่ใช่ "ผิด"
2. รัน GSM8K sample กับโมเดลของคุณ แล้วดู `finish_reason` — กี่ % เป็น `length`
3. เพิ่ม max_tokens แล้ววัดใหม่ — คะแนนขึ้นไหม ([82.3](#s82-3))
4. quantize โมเดลเป็น int8 แล้วเทียบคะแนน GSM8K ก่อน/หลัง ([82.5](#s82-5))
5. ตอบตัวเอง: benchmark ไหนตรงกับงานจริงของคุณ ([82.2](#s82-2))
6. หา eval ที่ temperature ไม่ใช่ 0 — วัดซ้ำ 3 ครั้งต่างกันแค่ไหน ([82.4](#s82-4))
7. เขียนรายงาน eval ที่ระบุ flag ครบให้คนอื่นทำซ้ำได้ ([82.6](#s82-6))

## 84.1 ตัวเลขทศนิยม — ช่วง vs ความละเอียด {#s84-1}

**dtype แต่ละแบบแลกกันระหว่าง "ช่วงที่เก็บได้" กับ "ความละเอียด"**

วัดจริง:

```
dtype     bytes    ช่วงสูงสุด        หมายเหตุ
fp32          4     3.40e+38     ละเอียดสูง
fp16          2     6.55e+04     ช่วงแคบ!
bf16          2     3.39e+38     ช่วงกว้างเท่า fp32
```

| dtype | bits | ช่วง | ความละเอียด |
|---|---|---|---|
| **fp32** | 32 | กว้างมาก | สูง |
| **fp16** | 16 | **แคบ** (สูงสุด 65504) | ปานกลาง |
| **bf16** | 16 | **กว้างเท่า fp32** | ต่ำกว่า fp16 |

**bf16 กับ fp16 ขนาดเท่ากัน (2 byte) แต่แบ่ง bit ต่างกัน** — bf16 ให้ bit
กับ "ช่วง" มากกว่า "ความละเอียด"

## 84.2 ทำไม fp16 overflow แต่ bf16 ไม่ {#s84-2}

[บทที่ 66.3](66-training-and-finetuning.md#s66-3) บอกว่า fp16 ต้องมี GradScaler แต่ bf16 ไม่ต้อง — นี่คือเหตุผล

วัดจริง:

```
ค่า 70000 ใน fp16: inf      ← overflow! (เกินช่วง 65504)
ค่า 70000 ใน bf16: 70144.0  ← ยังไหว (ช่วงเท่า fp32)
```

> ## นี่คือเหตุผลที่ bf16 ชนะ fp16 ในการเทรน
>
> **gradient/activation ที่มีค่าใหญ่จะ overflow เป็น inf ใน fp16** แล้วพังทั้ง
> การเทรน bf16 มีช่วงเท่า fp32 จึงไม่เจอปัญหานี้ (แลกกับความละเอียดที่น้อยลง
> ซึ่ง deep learning ทนได้)
>
> **การ์ด Ampere ขึ้นไปรองรับ bf16** — ถ้ามี ใช้ bf16 ง่ายกว่า fp16 + scaler
> ([บทที่ 66.3](66-training-and-finetuning.md#s66-3))

## 84.3 Quantization — น้ำหนักเล็กลงด้วย integer {#s84-3}

**quantization = เก็บน้ำหนักเป็น integer เล็ก ๆ + scale factor**

```
น้ำหนักจริง (fp32) → หาช่วง [min, max] → map ไป integer [-127, 127]
                                            + เก็บ scale ไว้แปลงกลับ
```

วัดจริง (น้ำหนัก 128 ค่า):

```
น้ำหนัก fp32: 512 bytes
int8 + scale: 132 bytes  (เล็กลง ~4 เท่า)
error เฉลี่ยหลังแปลงกลับ: 0.0080
```

**เล็กลง 4 เท่า error แค่ 0.008** — นี่คือเหตุผลที่ quantize คุ้ม

```python
scale = w.abs().max() / 127              # map ช่วงจริงไป int8
q = torch.round(w / scale).to(torch.int8)   # เก็บเป็น int8
deq = q.float() * scale                   # แปลงกลับตอนใช้
```

> ## ทำไมต้องมี scale — และทำไม block เล็กดีกว่า
>
> integer เก็บได้แค่ -127 ถึง 127 **scale คือตัวบอกว่า 1 หน่วย integer =
> เท่าไรจริง** ถ้าน้ำหนักในกลุ่มมีค่ากระจายมาก scale เดียวครอบไม่ดี error สูง
>
> **แก้โดยแบ่งเป็น block เล็ก ๆ แต่ละ block มี scale ของตัวเอง** — ยิ่ง block
> เล็ก scale ยิ่งพอดี error ยิ่งน้อย แลกกับต้องเก็บ scale มากขึ้น

## 84.4 dtype ที่เจอในวงการ serving {#s84-4}

| dtype | bits | ใช้ตอน |
|---|---|---|
| **fp32** | 32 | แทบไม่ใช้ตอน serve (เปลือง) |
| **bf16** | 16 | มาตรฐานของการเทรน/serve |
| **fp8** | 8 | serving รุ่นใหม่ (Hopper/Blackwell รองรับ) |
| **int8** | 8 | quantize น้ำหนัก |
| **int4 / MXFP4** | 4 | quantize แน่น (LLM ใหญ่บนการ์ดเล็ก) |

> **FP8 ต่างจาก int8** — fp8 ยังเป็นทศนิยม (มี exponent) จึงมีช่วงกว้างกว่า
> int8 เหมาะกับ activation ที่ค่ากระจาย ส่วน **MXFP4** เป็น fp4 ที่แชร์ scale
> เป็น block (microscaling) — เก็บได้แน่นมากโดยคุม error
>
> **การ์ดใหม่ (Hopper H100, Blackwell B200) มี Tensor Core ที่ทำ fp8 ได้เร็ว
> เป็นพิเศษ** — นี่คือส่วนหนึ่งที่ทำให้การ์ดใหม่เร็วกว่าตอน serve

## 84.5 KV cache ก็ quantize ได้ {#s84-5}

[บทที่ 47.4](47-gpu-memory-and-kv-cache.md#s47-4) บอกว่า KV cache กิน VRAM ตามจำนวนผู้ใช้ — **quantize
KV cache ลดตรงนี้ได้อีก**

```
KV cache fp16 → fp8: เล็กลงครึ่งหนึ่ง → รับคนได้ ~2 เท่า
```

| quantize อะไร | ผล | ระวัง |
|---|---|---|
| **น้ำหนัก** | โหลดโมเดลใหญ่ลงการ์ดเล็ก | คุณภาพตกเล็กน้อย |
| **KV cache** | รับคนได้มากขึ้น | context ยาวอาจเพี้ยน |
| **activation** | เร็วขึ้น (fp8 compute) | ต้อง calibrate |

> **KV cache dtype เป็น flag ที่ตั้งได้ใน vLLM** (`--kv-cache-dtype fp8`) —
> เพิ่มความจุผู้ใช้โดยแลกกับความแม่นเล็กน้อย ต้องวัด ([บทที่ 82.5](82-llm-evaluation.md#s82-5)) ว่า
> คะแนนตกเท่าไร คุ้มไหม

## 84.6 🔴 ต้องตรวจ numerical correctness หลังเปลี่ยน {#s84-6}

**quantize/เปลี่ยน dtype แล้วต้องพิสูจน์ว่ายังถูก** — ต่อจาก[บทที่ 82.5](82-llm-evaluation.md#s82-5)

```
1. รัน benchmark ก่อนเปลี่ยน (bf16)      → คะแนนฐาน
2. quantize (int4 / fp8)
3. รันซ้ำ → คะแนนตกกี่ %
4. ชั่งกับ VRAM/speed ที่ได้ → คุ้มไหม
```

| ตรวจ | ยังไง |
|---|---|
| output เพี้ยนไหม | เทียบ logit กับ baseline |
| **เคสขอบ** | ตัวเลขใหญ่, context ยาว ที่ precision ต่ำเพี้ยนง่าย |
| คะแนน benchmark | ตกเกินรับได้ไหม ([บทที่ 82.2](82-llm-evaluation.md#s82-2)) |

> **quantize แล้วตก 1-2% แลก VRAM 4 เท่ามักคุ้ม** — แต่ตัวเลขนี้ต้องวัด ไม่ใช่
> เดา บางงาน (เลข, code) ไวต่อ precision มากกว่างานอื่น **เปลี่ยน precision
> โดยไม่วัดคือการเดาสุ่มว่าคุณภาพยังโอเค**

# ภาคผนวก A · netcat (`nc`) — เครื่องมือดูของจริง

> `curl` รู้จัก HTTP และช่วยจัดการหลายอย่างให้เบื้องหลัง
> `nc` **ไม่รู้จักอะไรเลย** — มันแค่ต่อท่อ TCP แล้วส่ง byte ที่คุณป้อนไปตรง ๆ
>
> ความ "โง่" นี้แหละคือประโยชน์ของมัน เพราะมันไม่แอบทำอะไรให้

## A.1 nc คืออะไร {#sA-1}

นึกภาพ `cat` ที่ปลายท่อไม่ใช่ไฟล์ แต่เป็น **การเชื่อมต่อเครือข่าย**

```
cat  ไฟล์          →  พิมพ์เนื้อไฟล์ออกจอ
nc   host port     →  ส่ง stdin ไปที่ host:port แล้วพิมพ์สิ่งที่ตอบกลับออกจอ
nc   -l port       →  รอรับการเชื่อมต่อ แล้วพิมพ์สิ่งที่รับมาออกจอ
```

แค่นั้นจริง ๆ ไม่มีความรู้เรื่อง HTTP, TLS, redirect, cookie อะไรทั้งสิ้น

**สองโหมดที่ต้องแยกให้ออก:**

| โหมด | คำสั่ง | บทบาท |
|------|--------|--------|
| **client** | `nc HOST PORT` | ต่อออกไปหาคนอื่น |
| **server** | `nc -l HOST PORT` | เปิดพอร์ตรอคนอื่นมาต่อ |

## A.2 ⚠️ nc มีหลายยี่ห้อ และ flag ไม่เหมือนกัน {#sA-2}

นี่คือกับดักอันดับหนึ่งเวลาลอกคำสั่งจากอินเทอร์เน็ตมาแล้วใช้ไม่ได้

| ยี่ห้อ | สังเกตยังไง | หมายเหตุ |
|--------|-------------|----------|
| **OpenBSD netcat** | `nc -h` ขึ้น "OpenBSD netcat" | ค่าเริ่มต้นของ Debian/Ubuntu — บทนี้ใช้ตัวนี้ |
| GNU netcat | ขึ้น "GNU netcat" | flag ต่างพอสมควร |
| **ncat** (จาก nmap) | `ncat --version` | ฟีเจอร์เยอะสุด รองรับ TLS ด้วย |
| busybox nc | ในระบบเล็ก ๆ / container | มี flag น้อยมาก |

เช็คของคุณ:

```bash
nc -h 2>&1 | head -1
readlink -f "$(which nc)"
```

ตัวอย่างความต่างที่เจ็บที่สุด: **บางยี่ห้อต้องใช้ `-p`** (`nc -l -p 8080`)
แต่ OpenBSD ใช้ `nc -l 8080` เฉย ๆ

## A.3 Flag ที่ใช้จริง (OpenBSD netcat) {#sA-3}

| Flag | ทำอะไร | ใช้ตอนไหน |
|------|--------|-----------|
| `-l` | listen — เป็น server | ทำ server ปลอม / ดัก request |
| `-v` | verbose บอกว่าต่อติดไหม | เช็คพอร์ต |
| `-z` | แค่เช็คว่าต่อได้ ไม่ส่งข้อมูล | สแกนพอร์ต |
| `-w N` | timeout N วินาที | **ใส่ไว้เสมอ กันค้าง** |
| `-k` | รับต่อได้เรื่อย ๆ ไม่ปิดหลัง client แรก | server ปลอมที่ใช้หลายครั้ง |
| `-u` | ใช้ UDP แทน TCP | ทดสอบ DNS/syslog |
| `-n` | ไม่ต้อง resolve DNS | เร็วขึ้น ตัดตัวแปร |
| `-C` | **ส่ง CRLF ให้อัตโนมัติ** | พิมพ์ HTTP ด้วยมือ (ดู A.5) |
| `-N` | ปิดการเชื่อมต่อเมื่อ stdin หมด | บาง server รอจนกว่าจะปิด |
| `-q N` | รอ N วินาทีหลัง stdin หมดแล้วค่อยปิด | รอ response ให้มาครบ |

## A.4 ใช้ที่ 1 — ดักดู request ดิบ {#sA-4}

นี่คือสิ่งที่ใช้ใน[บทที่ 1](01-http-basics.md) หัว[ข้อ 1.9](01-http-basics.md#s1-9)

```bash
# หน้าต่างที่ 1 — รอรับแล้วเทลงไฟล์
nc -l -v 127.0.0.1 8099 > raw.bin

# หน้าต่างที่ 2 — ยิงอะไรก็ได้ใส่
curl --max-time 2 -d 'user=somchai' http://127.0.0.1:8099/login
```

### ⚠️ อ่านตรงนี้ก่อน ไม่งั้นจะงงแน่นอน

**`nc -l` จะเงียบสนิท ไม่แสดงอะไรเลย จนกว่าจะมีคนต่อเข้ามา**

ถ้าไม่ใส่ `-v` คุณจะเห็นแค่เคอร์เซอร์กะพริบ แยกไม่ออกเลยว่า

- กำลังรออยู่ตามปกติ ✅
- คำสั่งค้าง ❌
- พิมพ์ผิดแล้วมันรออะไรอยู่ก็ไม่รู้ ❌

**ใส่ `-v` เสมอ** แล้วมันจะบอกสถานะให้:

```
$ nc -l -v 127.0.0.1 8099
Listening on localhost 8099          ← บอกทันทีว่ารออยู่แล้ว
                                     ← จากนั้นเงียบ รอไปเรื่อย ๆ
                                     ← (ยิง curl จากอีกหน้าต่าง)
Connection received on localhost 60056
POST /login HTTP/1.1                 ← ข้อมูลเริ่มไหลออกมาตรงนี้
Host: 127.0.0.1:8099
User-Agent: curl/8.5.0
...
                                     ← curl ตัดสาย → nc จบการทำงานเอง
```

**ทำไมถึงเป็นแบบนี้** — `nc` ไม่ใช่โปรแกรมโต้ตอบ มันคือ**ท่อ** เหมือน `cat`
ที่รอ input จากคีย์บอร์ดแล้วไม่พิมพ์อะไรจนกว่าคุณจะพิมพ์

**ข้อความสถานะออกทาง stderr ส่วนข้อมูลจริงออกทาง stdout** — ออกแบบมาดีมาก
เพราะเวลาเขียนลงไฟล์ `raw.bin` จะมีแต่ byte ของ request จริง ไม่มีคำว่า
`Listening on...` ปนเข้าไป

**สามอย่างที่ตามมา:**

1. **รับได้ครั้งเดียวแล้วจบ** — พอ client ตัดสาย `nc` ออกจากโปรแกรมเลย
   ถ้าอยากให้รับต่อเรื่อย ๆ ใส่ `-k`
   ```bash
   nc -l -k -v 127.0.0.1 8099
   ```
2. **ใส่ `-w 10` กันลืม** — เลิกรอเองใน 10 วินาที ไม่ต้องกด Ctrl-C
3. **`curl` จะขึ้น `Empty reply from server`** เพราะ `nc` ไม่ได้ตอบอะไรกลับไป
   — เป็นเรื่องปกติ เราแค่ต้องการดู request ที่มันส่งมา ไม่ได้ต้องการ response

### ดูของที่ดักได้

```bash
cat -A raw.bin      # เห็น ^M$ = CRLF
xxd raw.bin | head  # เห็นเลขฐาน 16
```

**ทำไมต้องใช้ nc ทั้งที่มี `curl -v`**

`curl -v` แสดงสิ่งที่ curl **คิดว่า**มันส่ง ส่วน `nc` แสดงสิ่งที่**มาถึงปลายทางจริง ๆ**
ทุก byte รวมถึงตัวที่มองไม่เห็น — ต่างกันเมื่อคุณสงสัยว่ามีอะไรแปลก ๆ อยู่

## A.5 ใช้ที่ 2 — พูด HTTP ด้วยมือ {#sA-5}

เพราะ HTTP/1.1 เป็นข้อความ ([บทที่ 1.9](01-http-basics.md#s1-9)) คุณจึงพิมพ์เองได้

```bash
printf 'GET /api/books HTTP/1.1\r\nHost: 127.0.0.1\r\nConnection: close\r\n\r\n' \
  | nc 127.0.0.1 8080
```

**หรือใช้ `-C` แล้วไม่ต้องพิมพ์ `\r\n` เอง** — สะดวกกว่ามาก:

```bash
{ echo "GET /api/books HTTP/1.1"
  echo "Host: 127.0.0.1"
  echo "Connection: close"
  echo ""; } | nc -C 127.0.0.1 8080
```

`-C` แปลง `\n` ทุกตัวเป็น `\r\n` ให้ ตรงกับที่ HTTP ต้องการพอดี

**พิมพ์สดแบบโต้ตอบก็ได้** — ต่อแล้วพิมพ์ทีละบรรทัด:

```bash
nc -C 127.0.0.1 8080
GET /api/books HTTP/1.1
Host: 127.0.0.1
Connection: close
              ← กด Enter ให้บรรทัดว่าง แล้ว response จะพุ่งออกมา
```

> **ทำไมต้อง `Connection: close`** — HTTP/1.1 เปิดสายค้างไว้เผื่อยิงซ้ำ (keep-alive)
> ถ้าไม่บอกให้ปิด `nc` จะค้างรอต่อหลังได้ response แล้ว

## A.6 ใช้ที่ 3 — ทำ server ปลอมเพื่อทดสอบ client {#sA-6}

นี่คือการใช้งานที่มีค่าที่สุดสำหรับคนทำ API และ mobile app

### ตอบ error ที่จำลองยากในของจริง

```bash
# ทำ server ที่ตอบ 500 ครั้งเดียว
printf 'HTTP/1.1 500 Internal Server Error\r\nContent-Length: 11\r\n\r\nserver พัง' \
  | nc -l 127.0.0.1 8098

# อีกหน้าต่าง — ชี้แอป/สคริปต์ของคุณมาที่พอร์ตนี้
curl -s -o /dev/null -w 'client เห็น: HTTP %{http_code}\n' http://127.0.0.1:8098/
```

```
client เห็น: HTTP 500
```

**เอาไปทดสอบอะไรได้บ้าง** (โยงกับ[บทที่ 11](11-mobile-api-auth-design.md), 12, 19, 28):

| จำลอง | ทดสอบว่า client... |
|-------|--------------------|
| `401 Unauthorized` | เรียก refresh token แล้วยิงซ้ำครั้งเดียว ไม่วนลูป |
| `403 Forbidden` | **ไม่** พยายาม refresh |
| `429` + `Retry-After: 30` | รอจริงตามที่บอก |
| `500` + HTML แทน JSON | ไม่ crash ตอน parse |
| `426 Upgrade Required` | แสดงหน้าให้อัปเดตแอป |

### server ที่เงียบสนิท (ทดสอบ timeout)

```bash
nc -l 127.0.0.1 8097 > /dev/null &        # รับแล้วไม่ตอบอะไรเลย
curl -s -o /dev/null -w 'exit=%{exitcode} time=%{time_total}s\n' \
     --max-time 2 http://127.0.0.1:8097/
```

```
exit=28 time=2.001945s
```

exit 28 = timeout ตรงตาม[บทที่ 2.6](02-curl-basics.md#s2-6) — **ถ้าไม่ใส่ `--max-time` คำสั่งนี้จะค้างตลอดกาล**
นี่คือวิธีพิสูจน์ว่าโค้ดของคุณตั้ง timeout ไว้จริงหรือเปล่า

### ตอบช้า ๆ ทีละบรรทัด

```bash
{ printf 'HTTP/1.1 200 OK\r\nContent-Length: 20\r\n\r\n'
  sleep 5
  printf 'ครึ่งแรก'
  sleep 5
  printf 'ครึ่งหลัง'; } | nc -l 127.0.0.1 8096
```

ทดสอบว่า client รับมือกับ response ที่มาไม่ครบทีเดียวได้ไหม

> ถ้าต้องใช้บ่อย ๆ `mitmproxy` ([บทที่ 19](19-mitmproxy-mobile-traffic.md)) สะดวกกว่าเพราะเขียนสคริปต์ได้
> แต่ `nc` ชนะเรื่อง **ไม่ต้องติดตั้งอะไร และควบคุมได้ทุก byte**

## A.7 ใช้ที่ 4 — เช็คว่าพอร์ตเปิดไหม {#sA-7}

```bash
nc -z -v -w 2 127.0.0.1 8080
```

```
Connection to 127.0.0.1 8080 port [tcp/http-alt] succeeded!
```

```bash
nc -z -v -w 2 127.0.0.1 9999
```

```
nc: connect to 127.0.0.1 port 9999 (tcp) failed: Connection refused
```

**ประโยชน์เวลา debug** (โยงกับ[บทที่ 21.2](21-debugging-and-pitfalls.md#s21-2)): เมื่อ `curl` ขึ้น `Connection refused`
ใช้ `nc -z` แยกให้ชัดว่าปัญหาอยู่ชั้นไหน

```
nc -z ต่อไม่ได้   →  server ไม่ได้เปิด / port ผิด / firewall  ← ไม่ใช่เรื่อง HTTP
nc -z ต่อได้      →  ชั้น TCP ปกติ ปัญหาอยู่ที่ HTTP หรือ TLS
```

เช็คหลายพอร์ตพร้อมกัน:

```bash
nc -z -v -w 1 127.0.0.1 8080-8090 2>&1 | grep succeeded
```

> ⚠️ **สแกนพอร์ตเครื่องคนอื่นโดยไม่ได้รับอนุญาต อาจผิดกฎหมาย** ([บทที่ 22](22-ethics-and-limits.md))
> ใช้กับเครื่องตัวเองหรือระบบที่คุณดูแลเท่านั้น

## A.8 ใช้ที่ 5 — โอนไฟล์เร็ว ๆ ในเครือข่ายเดียวกัน {#sA-8}

```bash
# เครื่องรับ
nc -l 0.0.0.0 9000 > received.tar.gz

# เครื่องส่ง
nc -N 192.168.1.50 9000 < backup.tar.gz
```

`-N` สำคัญ — ปิดการเชื่อมต่อเมื่อส่งจบ ไม่งั้นฝั่งรับไม่รู้ว่าจบแล้ว

> ⚠️ **ไม่มีการเข้ารหัสและไม่มีการยืนยันตัวตนเลย** ใครดักกลางทางอ่านได้หมด
> ใช้ได้เฉพาะในเครือข่ายที่ไว้ใจได้ ถ้าต้องข้ามอินเทอร์เน็ตให้ใช้ `scp`/`rsync -e ssh`

## A.9 กับดักที่เจอบ่อย {#sA-9}

| อาการ | สาเหตุ | แก้ |
|-------|--------|-----|
| **`nc -l` ไม่ขึ้นอะไรเลย** | ปกติ! มันรออยู่เงียบ ๆ | ใส่ `-v` เพื่อให้บอก `Listening on...` |
| **ค้างไม่จบ** | HTTP keep-alive หรือ stdin ยังไม่ปิด | ใส่ `Connection: close`, `-w 5`, หรือ `-N` |
| `Address already in use` | มี process ค้างพอร์ตนั้นอยู่ | `fuser -k 8099/tcp` |
| **server ไม่ตอบทั้งที่พิมพ์ถูก** | ใช้ `\n` แทน `\r\n` | ใช้ `-C` หรือ `printf` ที่มี `\r\n` |
| `-l` ใช้ไม่ได้ | คนละยี่ห้อ | ลอง `nc -l -p 8099` |
| **รับได้แค่ครั้งเดียวแล้วปิด** | ค่าเริ่มต้นของ `-l` | ใส่ `-k` |
| ต่อ HTTPS แล้วเห็นแต่ byte มั่ว | nc ไม่รู้จัก TLS | ใช้ `openssl s_client` แทน (ดู A.10) |
| response มาไม่ครบ | nc ปิดเร็วเกินไป | ใส่ `-q 2` |

**ข้อที่ทำให้งงที่สุดคือข้อแรก** — `nc` ไม่รู้ว่า HTTP จบตรงไหน มันรอจนกว่าอีกฝั่งจะปิดสาย
จึงต้องบอกให้ปิดเสมอ

## A.10 nc ทำ HTTPS ไม่ได้ — ใช้ตัวนี้แทน {#sA-10}

`nc` ส่ง byte ดิบ ไม่ทำ TLS handshake ให้ ถ้าต่อพอร์ต 443 จะได้ขยะกลับมา

```bash
openssl s_client -connect example.com:443 -servername example.com -quiet
```

แล้วพิมพ์ HTTP ต่อได้เหมือนเดิม — `openssl s_client` ทำหน้าที่เป็น "nc ที่พูด TLS ได้"
(โยงกับ[บทที่ 7](07-tls-https.md) ที่ใช้คำสั่งนี้ดู certificate)

หรือใช้ `ncat` จาก nmap ซึ่งมี `--ssl` ในตัว:

```bash
ncat --ssl example.com 443
```

## A.11 ตารางสรุปเลือกเครื่องมือ {#sA-11}

| อยากทำ | ใช้ |
|--------|-----|
| ยิง HTTP ปกติ | **curl** |
| ดู byte ที่ส่งจริงทุกตัว | **nc -l** |
| พิมพ์ HTTP ด้วยมือ | **nc -C** |
| ทำ server ปลอมชั่วคราว | **nc -l** |
| ทำ server ปลอมที่มี logic | **mitmproxy** ([บทที่ 19](19-mitmproxy-mobile-traffic.md)) หรือ lab server |
| เช็คว่าพอร์ตเปิด | **nc -z** |
| ต่อ HTTPS ด้วยมือ | **openssl s_client** |
| ดักดู traffic ของ mobile app | **mitmproxy** ([บทที่ 19](19-mitmproxy-mobile-traffic.md)) |

## แบบฝึกหัด

1. รัน `nc -l 127.0.0.1 8099` เฉย ๆ ก่อน (ไม่ใส่ `-v`) รอสัก 5 วินาที
   — สังเกตว่าไม่มีอะไรขึ้นเลย จากนั้นกด Ctrl-C แล้วรันใหม่ด้วย `-v` เทียบกัน
2. ดัก request ของ `curl -d 'a=1' http://127.0.0.1:8099/x` แล้วนับว่ากี่ byte
   ยืนยันด้วย `xxd` ว่า `Content-Length` ตรงกับความยาว body จริง
3. พิมพ์ `GET /api/books` ด้วยมือให้สำเร็จ ทั้งแบบ `printf` และแบบ `nc -C` แบบโต้ตอบ
4. ลองไม่ใส่ `Connection: close` — เกิดอะไรขึ้น แล้ว `-w 3` ช่วยได้ไหม
5. ทำ server ปลอมที่ตอบ `429` พร้อม `Retry-After: 5`
   แล้วเขียนสคริปต์ curl ที่อ่านค่านั้นแล้วรอจริง (โยงกับ[บทที่ 20.7](20-shell-scripting-for-curl.md#s20-7))
6. ทำ server ที่ตอบ header ครบแต่ **ไม่ส่ง body เลย** ทั้งที่ประกาศ `Content-Length: 100`
   — client ของคุณค้างไหม ควรค้างไหม
7. ใช้ `nc -z` เช็คพอร์ต 8080-8090 บนเครื่องตัวเอง ว่าเปิดอันไหนบ้าง
8. เทียบ output ของ `curl -v` กับสิ่งที่ `nc -l` ดักได้จาก request เดียวกัน
   — มีอะไรที่ `curl -v` ไม่แสดงให้เห็นบ้าง
9. ใช้ `openssl s_client` พิมพ์ HTTP ด้วยมือใส่เว็บ HTTPS สักเว็บ (ของตัวเองหรือ `example.com`)
